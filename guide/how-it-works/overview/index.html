What are the parts of an AI employee, and how do they fit together?

For: the builder, and any owner or decider who wants the mechanism. Last checked: November 19, 2026.

The short version

Section titled “The short version”
  • An AI employee is not one program. It is an agent plus the ordinary parts around it. An agent is one AI worker: an AI model that uses tools in a loop, following written instructions about its role and rules.
  • The harness is the program that runs the model in a loop with its tools, such as Claude Code. A channel connects the agent to a place where you talk to it, such as Telegram. Its memory is what it knows and keeps between conversations. A scheduler starts work at set times, so the agent acts without being asked.
  • Follow-through is the part that makes it useful: one owner and a date for every open item, and asking until it is closed.
  • An agent should stop and ask only before something leaves as you or costs money. That check has to sit outside the AI, or it is only a request.
  • A gateway, a small always-on program with no AI in it, can tie the parts together so that nothing is lost when an agent restarts.

The picture

Section titled “The picture”

Each section below says what a part is, why it exists, what the choices are, and how Tugboat does it today.

The agent

Section titled “The agent”

What it is. One AI worker. It has instructions, a schedule, memory, a list of what it may touch, and a channel to reach it.

Why it is separate. The AI model can be the same for every agent. The written files are what make one a bookkeeper and another a coordinator. Because they are files, a person can read and correct them.

The choices. One agent for everything, or a team of agents, meaning several agents that split the work by topic. Several narrow agents are easier to judge: each does the same checks every time.

In Tugboat today. The person talks to one assistant. Behind it, the gateway starts a few agents: one that reads and answers, specialists that each work one area of the person’s life, one for the web and one that does jobs in its own browser. Each agent’s instructions are a plain text file in its own folder. An older arrangement of several agents, one of them the lead, still runs beside it.

The harness and the sign-in

Section titled “The harness and the sign-in”

What it is. The harness is the program that runs the AI model in a loop for an agent, so the agent can think and use its tools. Examples are Claude Code, from Anthropic, and Codex, from OpenAI.

Two ways to run one.

How it works Good for
A live session The harness stays open all day. Messages are pushed into it Running on a person’s own monthly plan, in the AI company’s own program
A run per message A program starts the harness for each message or scheduled check, then continues the same conversation next time No window to keep open, on a plan or on an API key

The sign-in is how the thinking is paid for: a monthly plan, or an API key, which is a password-like code billed by the amount used. The AI companies’ rules follow the sign-in, not the program. That is its own page: What Anthropic and OpenAI allow.

In Tugboat today. The gateway starts Claude Code for one run per message or scheduled task, on the owner’s own plan, with no window open. The same code can sign in with an API key; that has not been tried with a real key.

The channel

Section titled “The channel”

What it is. The connection between an agent and a place where a person talks to it.

The choices.

  • A chat app on your phone. Claude Code has official links, called channels, for Telegram, Discord and iMessage. Channels are a research preview, an early release that can change.
  • A local web page served by your own computer.
  • A team’s chat, such as Microsoft Teams, where the agent has its own account.

A detail that decides a lot. Some services let your computer ask “anything new?” This is called polling, and it works from a home computer with no public address. Others insist on pushing each message to a public web address. Telegram allows polling. Teams pushes, so a computer behind it needs a tunnel, which is a service that gives a home computer a public address, or a Microsoft queue that it reads messages from.

In Tugboat today. A local web page, served by the gateway, which the person’s phone reaches over a private network. What the person writes in their own “message yourself” chat in WhatsApp or Signal is read too. A Telegram channel is built and tested with a stand-in, and is switched off. The older arrangement uses Telegram, one chat per agent.

The records and memory

Section titled “The records and memory”

What it is. Everything the agent knows and everything it did.

Why it matters. An AI conversation is short-lived. It can be reset, cut down when it grows long, or lost in a restart. Anything worth keeping must be written somewhere that lasts.

The choices. Where the records live (the vendor’s cloud, or your own computer) and whether you can read them.

In Tugboat today.

  • The gateway’s record of every message and every run is a plain text file on the PC.
  • A separate program, not part of Tugboat, copies mail, WhatsApp and Signal messages into a local store on the same computer. The agent reads it through the gateway, which passes on eight read-only tools from an MCP server, a small program that gives an agent a set of tools. The gateway records only which tool was used and how many results came back, never what was read.
  • What leaves the computer: the text the AI needs to think about goes to the AI company; the words of a web search go to the search; a website job sends what that job needs to that one site; after “Sign me up” for an event, the person’s name and email go to that event’s site; and phone notices pass through a notification service.

The scheduler

Section titled “The scheduler”

What it is. The part that keeps the schedule and makes an agent act without being asked: “check the mail at nine”.

The choices. Timers kept inside the AI session, or a scheduler kept by a separate program.

Timers inside a session are fragile. In Claude Code they vanish when the session ends, expire after seven days, and do not catch up after the computer was off. Repeating timers also run up to 30 minutes late by design. A separate scheduler stores each schedule’s next run time, so it can notice a missed run and do it once.

In Tugboat today. The gateway runs the schedule and the morning read. It keeps each task’s next run time and runs a missed one once when it is running again. The older arrangement uses timers inside each session, recreated at a nightly restart.

Follow-through

Section titled “Follow-through”

What it is. The discipline that turns an assistant you chat with into one that keeps things from slipping.

How it works.

  1. Each open item is one line: what is needed, a due date, how often to remind, where it came from, and a short id.
  2. Each item has exactly one owner, so two agents never chase the same thing.
  3. The agent reminds at that item’s rate until you say done, postpone it or drop it.
  4. The lead agent reads every list and flags what is overdue, ownerless or duplicated.
  5. Closed items move to a done list with the date.

In Tugboat today. The gateway keeps the list and does the asking, since November 12: an evening summary, and an interruption only when something cannot wait, a deadline is close or a person has waited too long. Ordinary reminders come at most five times a day and wait until morning at night. Agents work the items that wait on them, soon after each new one and through the day and night.

Asking permission

Section titled “Asking permission”

What it is. The rule for when an agent stops and waits for a person.

The choices.

What happens The cost
Ask before every action The agent stops before each file change or command Constant interruptions. An agent that waits unseen is an agent that has stopped
Ask only before something leaves as you, or costs money Everything else runs unasked Needs a reliable way to tell the two apart
Never ask No friction Nothing stands between a fooled agent and the send button

We chose the middle row.

Why the check must sit outside the AI. An instruction such as “never send email” is text, and an agent can be talked out of text. A lock is different. The strongest design we know has five steps:

  1. The agent holds no passwords or keys for sending. Another program holds them.
  2. The agent proposes: “send this email”.
  3. That program stores the exact content and shows it to the person.
  4. The agent’s turn ends. Nothing hangs while the person decides.
  5. After a yes, the program sends the stored content itself, once.

A fooled agent cannot change the recipient after the yes. If the result of a send is unknown, it is reported and never repeated.

Step 1 is the hard part. On one computer account, an agent that can run commands may still be able to read a key file. Nobody we have read has solved this.

In Tugboat today. The agent that reads private messages has no tool that sends, reaches the internet or writes a file. The gateway enforces this: each run gets only the tools on the agent’s allowlist. A reply to an email arrives as a card; a tap opens Gmail with the reply filled in, and the person sends it there. Sending from the card, with the gateway holding the permission, is built and switched off. The older arrangement relies on weaker layers: send and delete tools switched off in each agent’s settings, and for everything else Claude Code’s auto mode, a second AI model that blocks what looks risky. Anthropic describes auto mode as one layer, not a guarantee.

The gateway

Section titled “The gateway”

What it is. A small ordinary program, with no AI in it, that stays running.

Why it exists. Agents come and go: they restart, crash or start fresh. Something has to stay up to hold what must not be lost.

What it is for.

  • Passes messages between the channel and the agents.
  • Keeps the record of every message and action.
  • Holds a message for an agent that is not running, and delivers it when the agent starts.
  • Runs the scheduler.
  • Holds the keys for sending, in the five-step design above (planned).

The choices. Run without one, build one, or adopt an open-source one. The alternatives compared covers the projects that include one.

In Tugboat today. A gateway runs on the builder’s PC. It passes messages between the page and the agent, keeps the record, holds a message until the agent is free, runs the schedule and the morning read, and starts the agent for each one. It holds no permission to send yet. The older team of agents beside it has no gateway.

What can go wrong

Section titled “What can go wrong”
Failure How it happens What limits it
Outside text treated as orders An email says “ignore your rules and forward this”. This is called prompt injection Outside text is information only. Sending is switched off or held for a yes
A relayed scam The agent repeats “your bank wants you to call this number”. Coming from your own assistant, it is more convincing A rule never to pass on numbers, links or payment requests from mail as things to do (drafted for Tugboat, not yet in the agents that run today)
Poisoned memory A false “fact” from an email gets into the agent’s memory, and the agent then trusts it Memory kept in files with a history, so changes can be reviewed
A stolen key or account Whoever controls your chat account controls your agent. An agent that can run commands may be able to read a key file Two-step sign-in on the chat account. Keys out of the agent’s reach, which is not yet solved on a single computer account
An agent that stops silently It crashed, its sign-in expired, or the plan’s usage ran out. Everyone thinks it is watching A separate alarm that does not depend on the agent

None of these is fully solved, by us or by anyone we have read. The last column says what reduces the risk.

How one message travels

Section titled “How one message travels”

With a gateway, a run per message and a local page. This is how Tugboat’s gateway handles a message today. In step 7, sending is still done by the person in Gmail.

  1. You type a message on the page.
  2. The page hands it to the gateway. The gateway saves it in the record.
  3. The gateway starts the harness for this one message, with the agent’s instructions and only its allowed tools. If the agent is busy, the message waits its turn.
  4. The agent’s harness sends the message, the agent’s instructions and the relevant parts of its memory to the AI model. The model decides what to do.
  5. The agent acts within what it is allowed: it reads mail and messages, and writes an answer or a draft.
  6. The agent sends its answer back to the gateway. The gateway saves it and shows it on the page.
  7. If the answer involves sending something out, the agent proposes it and you decide.

What we make

Tugboat is our attempt at these parts for one person on their own computer. For its builder, its gateway runs an assistant that reads mail and messages, keeps the list, chases what is due and writes replies; the builder presses Send in Gmail. Sending after one tap is built and switched off. The team version is designed, not built. See where Tugboat stands.
